## Context

当前项目已经具备几块关键基础：后端装备生成/打造可以按装备来源、等级和稀有度生成合法装备；地图编辑和怪物包系统已经能在 playable WebApp 中生成地图怪包；技能宝石和宝石道具已经能参与战斗；装备词缀运行时接入仍有独立 change 正在收尾。

缺口在于这些系统还没有组成玩家视角的刷宝循环。当前 `LootRuntime` 仍以宝石为中心，`CombatSession` 的掉落结构是 `DroppedGem`，WebApp 侧地图生怪会计算怪物生命/倍率，但后端战斗仍使用最小测试怪。这个 change 要把地图等级、怪物等级、掉落表、装备 item level、宝石等级、地图入口、主界面/地图选择和自动存档连成一条后端 canonical 链路。

## Goals / Non-Goals

**Goals:**

- 建立 1-59 成长地图阶段和 60+ 异界时刻阶段。
- 保证 `起始区域 I` 永久在线、免费、可无限刷，作为断票兜底。
- 为主界面增加“继续游戏 / 新游戏 / 地图选择 / 当前进度”这类入口，并为地图选择界面展示已解锁阶段、地图入口数量、地图等级、怪物等级和掉落预览。
- 新增后端 `MapRunContext` 或等价结构，作为地图等级、怪物等级、掉落表和奖励加成的唯一来源。
- 将怪物数值曲线、装备掉落、宝石等级掉落和地图入口掉落配置化。
- 将击杀掉落从 `DroppedGem` 扩展为通用掉落，支持宝石、装备和地图入口。
- 自动保存玩家进度、解锁状态、地图入口、背包、装备、数独盘、当前运行安全状态和设置。
- playable WebApp 使用后端 canonical 战斗和掉落结果，前端只负责选择、展示、动画和拾取交互。

**Non-Goals:**

- 不实现完整赛季系统、Atlas、复杂地图词缀、通货经济、交易、角色职业树或多角色账号。
- 不把地图模板数量误解为玩家可玩层级数量；V1 可复用底层地图模板。
- 不引入 2.5D、等距、透视压缩或非 2D top-down 玩法表现。
- 不使用 skill editor、`/skill-editor`、`dist-skill-editor` 或端口 `8765` 作为验证入口。
- 不重写现有装备词缀生成规则；掉落只决定装备来源、等级和稀有度，再调用现有生成器。

## Decisions

1. 玩家进度分成“成长地图”和“异界时刻”两段。

   1-59 使用成长阶段：`起始区域 I`、`起始区域 II`、`边境区域`、`深层区域`、`高危区域 I`、`高危区域 II`。60+ 使用时刻阶段：`时刻 1` 到 `时刻 6`、`时刻 7-1`、`时刻 7-2`、`时刻 8-1` 到 `时刻 8-4`。

   理由：玩家早期需要推进感和兜底地图，60 后才进入刷宝循环。这样比把 1-100 全部暴露为地图等级更接近火炬之光：无限的体验。

   备选方案：玩家直接选择 1-100 地图等级。该方案配置简单，但玩家层级太碎，掉落和 UI 难以做出清晰阶段感。

2. `起始区域 I` 永久免费。

   `起始区域 I` 不消耗地图入口，不会被锁定，也不会因为自动存档或门票耗尽而不可进入。它可低概率掉 `起始区域 II` 入口。

   理由：刷宝游戏不能让玩家因为断票无法玩。起始区域 I 是装备、宝石和入口资源的兜底循环。

3. 后端 map run context 是唯一真实来源。

   后端生成或加载 `MapRunContext`，包含 `map_id`、`stage_id`、`map_level`、`monster_level`、`timemark`、`loot_profile`、`reward_level_bonus`、`entry_cost` 和 seed。怪物实例、战斗结果和掉落都引用这个上下文。

   理由：AGENTS.md 明确要求 playable WebApp 不维护前端本地战斗运行时镜像。现有 `webapp/mapSpawnRuntime.ts` 可以保留为渲染/过渡适配，但不能决定真实 HP、伤害、目标或掉落。

4. 怪物等级和奖励等级分开。

   `monster_level` 控制怪物生命和伤害；`item_level` 来自 `monster_level + reward_level_bonus + rarity/boss bonus`。普通怪物等级可在 85 左右进入高时刻上限，高时刻主要增加掉落倍率、奖励等级和 Boss 产出。

   理由：装备已有 T1 86、至臻 100 的门槛。普通地图怪物不需要无限涨级，特殊产出可以通过奖励等级达到 86 或 100。

5. 装备掉落复用现有装备生成器。

   掉落系统只选择装备 `source`、`item_level` 和 `rarity`，再调用 `EquipmentGenerator.generate(source, item_level, rarity)`。词缀 tier、容量、进阶/至臻限制继续由 `equipment-affix-generation` 定义。

   理由：避免复制装备词缀门槛，保持 GM 生成、打造和掉落装备使用同一套规则。

6. 宝石掉落等级由地图等级配置映射。

   掉落系统从配置读取每个阶段的宝石等级权重。1-59 逐步掉 Lv1-Lv12，时刻阶段掉 Lv11-Lv20。普通玩家可见宝石等级仍受现有 `GemInventory` 1-20 限制。

   理由：当前 `LootRuntime.generate_drop()` 固定 Lv1，不适合刷宝。配置化映射可以让掉落节奏独立于技能内部 1-40 level table。

7. 通用掉落结构替代 gem-only 结构。

   新结构应能表达：

   - `kind = gem`
   - `kind = equipment`
   - `kind = map_entry`

   Web/API presentation 根据 kind 展示详情和拾取动作。旧 `DroppedGem` 可通过兼容适配逐步迁移，但新测试以通用掉落为准。

8. 自动存档采用后端状态快照。

   存档至少覆盖：玩家进度、已解锁阶段、地图入口库存、GemInventory、装备列表、装备槽、数独盘位置、当前选中地图、最近安全点、日志摘要和版本号。触发点包括进入地图、击杀产生掉落、拾取、装备/卸装、宝石上盘/下盘、地图解锁、退出/返回主界面。

   理由：当前 WebApp 状态主要是内存态。刷宝循环需要玩家能够关闭后继续游戏，同时避免刷新页面丢失门票或装备。

9. 主界面和地图选择先做功能型界面。

   主界面提供继续、新游戏、地图选择和当前存档摘要。地图选择显示成长地图和时刻节点，明确免费/消耗入口、已锁定原因、地图等级、怪物等级、掉落重点和可进入状态。

   理由：这项 change 的目标是可玩的刷宝体验，不只是后端模拟。玩家必须能选择地图、看懂进度并开始一局。

## Risks / Trade-offs

- 前端已有本地地图生怪逻辑 -> 通过后端 canonical map run 输出逐步接管真实结果，前端只保留渲染适配和临时 fallback，并加测试证明 playable path 不调用前端真实掉落/数值逻辑。
- 当前工作区有大量已有改动 -> 实现时严格限定 change 范围，不回滚无关文件，优先在新文件和明确接入点做小步迁移。
- 通用掉落会触及 inventory/presentation/WebApp 多处 -> 先保持 gem 拾取兼容，再扩展 equipment/map_entry 拾取，测试覆盖每种 kind。
- 自动存档可能引入迁移问题 -> 存档需要版本号和缺字段默认值；旧无存档状态应自动创建新游戏。
- 前端验证成本上升 -> 任何 UI/可视改动必须启动 playable WebApp，截图保存到 `artifacts/screenshots/`。

## Migration Plan

1. 新增配置和纯后端模型，不改变现有 WebApp 入口默认行为。
2. 引入通用掉落结构，同时保留旧宝石掉落读取兼容。
3. 接入地图选择启动 map run，让后端创建怪物实例、战斗上下文和掉落上下文。
4. 让 WebApp 主界面/地图选择消费后端状态；战斗视图显示后端 map run。
5. 接入自动存档，先覆盖安全状态，再扩展到运行中掉落/地图入口。
6. 删除或隔离 playable path 中的前端真实掉落/数值决策，保留非 canonical 工具代码必须命名并测试隔离。

## Open Questions

- 时刻 8 的四个挑战层是否需要不同名称，还是先用 `时刻 8-1` 到 `时刻 8-4`。
- 自动存档是否只保留一个存档槽，还是主界面需要多存档槽。V1 建议单槽。
- 地图入口是否作为背包物品展示，还是作为地图选择界面的计数资源展示。V1 建议先作为地图选择资源展示。
